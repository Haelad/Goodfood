# Участие в разработке Goodfood

Goodfood — учебный pet-проект. Я рад исправлениям, идеям и замечаниям, но отвечаю на них в свободное время, поэтому быстрого ответа не обещаю.

Участвуя в проекте, вы соглашаетесь соблюдать [Кодекс поведения](CODE_OF_CONDUCT.md).

## С чего начать

1. Посмотрите [открытые issues](https://github.com/Haelad/Goodfood/issues). Возможно, ваша идея или проблема уже там.
2. Для небольших исправлений (опечатка, документация, тест) можно сразу открывать Pull Request.
3. Для крупных изменений (новая функциональность, смена архитектуры) сначала создайте issue и опишите идею. Так вы не потратите время на изменения, которые не впишутся в проект.

Хорошие места для первого вклада: тесты ([#42](https://github.com/Haelad/Goodfood/issues/42)), документация ([#39](https://github.com/Haelad/Goodfood/issues/39), [#21](https://github.com/Haelad/Goodfood/issues/21)).

## Как сообщить об ошибке

Создайте issue по шаблону **Bug report** и укажите:

- что вы делали (по шагам);
- что ожидали получить и что получили;
- окружение: ОС, браузер, запуск через Docker или локально;
- текст ошибки или скриншот, если есть.

Уязвимости в issues не публикуйте, порядок описан в [SECURITY.md](SECURITY.md).

## Как предложить улучшение

Создайте issue по шаблону **Feature request**: опишите задачу, которую хотите решить, и желаемый результат. Описание проблемы важнее описания реализации.

## Настройка окружения

Требуется Python 3.12, [Poetry](https://python-poetry.org/docs/#installation), Docker и Docker Compose.

```bash
git clone https://github.com/<ваш-аккаунт>/Goodfood.git
cd Goodfood
poetry install
```

Создайте файл `.env` по шаблону из [README](README.md#-запуск). Файл с секретами в репозиторий не попадает, он указан в `.gitignore`.

Запуск проекта:

```bash
docker compose up --build
```

## Порядок работы

1. Сделайте форк репозитория.
2. Создайте ветку от актуальной `master`:
   ```bash
   git checkout -b feature/короткое-название
   ```
   Для исправлений используйте префикс `fix/`, для документации `docs/`.
3. Внесите изменения. Одна ветка решает одну задачу.
4. Проверьте код (см. ниже).
5. Закоммитьте с понятным сообщением, что именно изменено и зачем.
6. Отправьте ветку в свой форк и откройте Pull Request в `master`. Заполните шаблон PR и укажите номер связанного issue, например `Closes #42`.

## Стиль кода

В проекте настроены `black`, `isort` и `ruff` (конфигурация в `pyproject.toml` и `.pre-commit-config.yaml`), длина строки 88 символов.

Проверку можно запускать автоматически перед каждым коммитом через [pre-commit](https://pre-commit.com/). Пакет в зависимости проекта не входит, установите его отдельно:

```bash
pip install pre-commit
pre-commit install
```

Дополнительно:

- Не переписывайте работающий код только ради стиля. Изменения должны быть связаны с задачей PR.
- Не добавляйте новые зависимости без необходимости. Если добавляете, объясните зачем в описании PR.
- Не коммитьте секреты, `.env`, дампы базы данных и загруженные пользователями файлы.

## Тесты

Тесты написаны на `pytest` с `pytest-django` и `factory_boy` и лежат в папке `tests/`. Для них нужна настроенная база PostgreSQL (параметры берутся из `.env`).

```bash
poetry run pytest
```

Правила:

- Новая функциональность должна сопровождаться тестами, исправление ошибки — тестом, который воспроизводит эту ошибку.
- Перед отправкой PR убедитесь, что тесты проходят.
- Если тест не проходит по причинам, не связанным с вашими изменениями, укажите это в PR.

## Миграции

Если вы меняете модели, добавьте в PR файл миграции. Обратите внимание: папка `apps/goodfood/migrations/` сейчас указана в `.gitignore`, поэтому при создании миграций уточните в issue или PR, как с ними поступить.

## Проверка Pull Request

Я смотрю, решает ли PR заявленную задачу, проходят ли тесты и не усложняет ли он проект без необходимости. Могут быть вопросы или просьбы внести правки. Это нормальная часть процесса.

Если PR долго остаётся без ответа, напишите в комментариях к нему.
