# Project: Goodfood

Goodfood — учебный backend-проект на Django.

# Infrastructure

Проект разворачивается через Docker Compose.

В инфраструктуре используются:

* Django application
* PostgreSQL
* Redis
* Nginx
* Certbot / Let's Encrypt

Nginx используется как reverse proxy и для работы с HTTPS.

В проекте ранее использовалась конфигурация HTTP/2:

```nginx
listen 443 ssl;
http2 on;
```

Не следует автоматически считать это единственно правильной конфигурацией. При изменении инфраструктуры необходимо ориентироваться на актуальную версию Nginx и документацию.

# Testing

Для тестирования используются:

* pytest
* pytest-django
* factory_boy

В pytest используется Django settings module проекта.

Пример актуальной конфигурации, если она не была изменена:

```toml
[tool.pytest.ini_options]
testpaths = ["./tests"]
python_files = ["test_*.py"]
addopts = "-ra -q --create_db"
DJANGO_SETTINGS_MODULE = "config.settings"
django_find_project = true
```

Не считать эту конфигурацию неизменной: перед рекомендациями по pytest проверяй актуальный файл конфигурации в репозитории.

# Current testing focus

Одна из текущих областей обучения — написание и отладка Django-тестов.

Особенно важно не просто заставить тест пройти, а понимать:

* как pytest-django создаёт тестовую БД;
* чем отличаются `create`, `build`, `build_batch` и `create_batch` в factory_boy;
* как формируются primary key;
* какие объекты реально сохраняются в БД;
* как связаны Django ORM, factories и URL;
* почему тест может вести себя иначе при использовании factory_boy;
* где заканчивается проблема теста и начинается проблема production-кода.

Если при работе с тестами возникает ошибка, сначала нужно выяснять механизм её возникновения, а не сразу менять fixture/factory до тех пор, пока тест случайно не пройдёт.

# Learning vs boilerplate

Не весь код проекта имеет одинаковую учебную ценность.

Если я изучаю конкретную технологию или концепцию, код, связанный с ней, должен в первую очередь писаться мной.

Например:

* если изучается Django ORM — я должен писать ORM-запросы;
* если изучается Django views — я должен самостоятельно реализовывать views;
* если изучается тестирование — я должен писать тесты;
* если изучается factory_boy — я должен самостоятельно разбираться с factories;
* если изучается Docker — я должен самостоятельно понимать и изменять Docker-конфигурацию.

Но стандартный boilerplate можно переиспользовать.

Например:

* типовой Docker Compose;
* стандартный Nginx;
* CI/CD;
* повторяющиеся конфигурационные файлы;
* стандартный проектный каркас;
* шаблонные настройки инструментов.

Не нужно заставлять меня вручную писать код только ради количества набранных строк.

Главный критерий:

> Я должен самостоятельно писать тот код, который развивает навык, изучаемый сейчас.

# Important project principle

Не следует преждевременно усложнять архитектуру.

Если существующий код решает задачу и не создаёт существенной проблемы, не нужно автоматически переписывать его ради:

* большей абстрактности;
* «красивой» архитектуры;
* паттернов ради паттернов;
* преждевременной оптимизации;
* соответствия чужому стилю.

Если есть архитектурная проблема, её нужно объяснить отдельно и показать, почему она действительно является проблемой.

# AI usage

AI используется как инструмент обучения, а не как замена программированию.

Нежелательный цикл:

```text
Задача
↓
Claude пишет решение
↓
Я читаю объяснение
↓
Мне кажется, что я понял
```

Предпочтительный цикл:

```text
Задача
↓
Я понимаю требования
↓
Я предлагаю план
↓
Я пишу код
↓
Я получаю ошибку
↓
Я анализирую ошибку
↓
Claude даёт подсказку
↓
Я исправляю код
↓
Я объясняю, почему решение работает
↓
Я решаю похожую задачу самостоятельно
```

Если я регулярно пытаюсь перескочить сразу к готовому решению, Claude должен возвращать меня к самостоятельной попытке.
